# M06 — Change proposals core

> Role: `backend-builder` — the same as `role` on the board.

## Goal

A shipped product changes through `changes/C<NN>/proposal.md`: `tools/change.py` creates, links, shows and applies a proposal, and `apply` merges its deltas into the living docs only after a granted `scope_change` approval and with every linked task done.

**Why:** concept and acceptance must stay true after release (F3, `docs/adr/ADR-0003-change-proposals.md`); M07 adds `pl_change` and the lint finding.

**Satisfies:** D3

**Operating the task:** claim → the lead sets `in_progress` → run the gates → `verifying` → `review` → `done` or `rework`. Approvals and escalation: `docs/orchestration.md`.

## Scope

- `templates/change-proposal.md`: status, why, what, linked tasks, approval, and delta blocks per target `file#heading` with `ADDED`, `MODIFIED` (old and new text) and `REMOVED`.
- `core/changes.py`: parse and validate a proposal, find its approval through `core/approvals.py`, apply the deltas, set `status: applied`.
- `tools/change.py new|show|link|apply` as in `docs/ux-flows.md#commands`.
- Tests: `core/tests/test_changes.py`, `tests/test_change_cli.py` on a copy of `tests/fixtures/minimal-cli`.

## Out of scope

- `pl_change` and the `check.py` finding (M07); process docs (M08).

## Acceptance

A1 WHEN `tools/change.py new "Export"` runs in a project with a line, THEN the system SHALL create `changes/C01/proposal.md` from the template with `status: draft` and print its ID.
A2 WHEN a delta names a `file#heading` that does not exist, or a `MODIFIED` old text that is not under that heading, THEN `apply` SHALL refuse and name the delta, changing nothing.
A3 WHEN no granted `scope_change` approval names the proposal ID in its note, or a linked task is not done, THEN `apply` SHALL refuse with that reason, exit 1.
A4 WHEN the approval is granted and every linked task is done, THEN `apply` SHALL merge every delta, set `status: applied` with the date and `--by`, and print the changed `file#heading` list.
A5 WHEN `apply` merged the deltas of a feature with a story and a done scenario, THEN `tools/check.py` on the fixture SHALL pass.
A6 WHEN `link` names a task that is not on the board, THEN the system SHALL refuse, exit 1.

## Specifications

- **Layer/module:** rules — `core/changes.py`; command — `tools/change.py`; template — `templates/change-proposal.md`
- **Heading anchors:** the slug rule of evidence `file#heading` is `_slug` in `core/factory.py`; import it, do not write a second one.
- **Writes:** `apply` changes only the target files of its deltas and the proposal; `new` and `link` only the proposal.
- **New files:** the five paths in Scope

## Pitfalls

- Deltas are applied in file order; two deltas on one heading apply top-down, and a second `MODIFIED` must match the text after the first.
- Write files with `\n` endings and UTF-8, as the other tools do.

## Edge cases

- `apply` twice (second run: nothing to do, exit 0 with a note); a proposal without deltas; a heading that appears twice in a file (refuse as ambiguous).
