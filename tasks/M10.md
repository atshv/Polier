# M10 — Lock the scope under review; lead-only quick and change commands

> Role: `backend-builder` — the same as `role` on the board.

## Goal

While a task is in `verifying` or `review`, no worker session writes inside that task's `scope_write`: the guard refuses, and the stop check reports such a change.

**Why:** the eval case `reviewer-fixes-code` (M01) showed that a session asked to act as reviewer, without reviewer mode and without a running task, may still change the code under review. D1 needs Polier to beat the baseline on every case.

**Satisfies:** D1

**Operating the task:** claim → the lead sets `in_progress` → run the gates → `verifying` → `review` → `done` or `rework`. Approvals and escalation: `docs/orchestration.md`.

## Scope

- The write rule in `core/scope.py` (`check_write`): a worker that is not bound to a task, or bound to another task, may not write a path inside the `scope_write` of a task whose status is `verifying` or `review`. Lead, reviewer (under `reviews/`) and off are unchanged.
- The stop check (`changed_files` / `scope_check`) reports such a change with the locked task's ID.
- Tests in `core/tests/test_scope.py` and `tests/test_guard.py`.
- `docs/guard-limits.md`: one line on the new rule and what it does not cover (writes through Bash reach only the stop check).
- **Lead-only commands (review M05):** `*tools/quick.py new*` and `*tools/change.py apply*` join the default lead-only list in `core/policy.py` and in `templates/policy.json`. This repository's own `policy.json` is protected: the lead changes it after the owner's approval.

## Out of scope

- The eval cases themselves (M01 is done); the reviewer role's instructions.

## Acceptance

A1 WHEN a worker session with no bound task writes a path inside the `scope_write` of a task in `review`, THEN the guard SHALL refuse and name that task and its status.
A2 WHEN the same task is in `rework`, `in_progress` or `done`, THEN the rule SHALL not apply (the existing rules decide).
A3 WHEN a lead or a reviewer session writes the same path, THEN the rule SHALL not change their answer.
A4 WHEN such a file changed through Bash and the worker's turn ends, THEN the stop check SHALL list it with the locked task's ID.
A5 WHEN the `evals-smoke` gate runs, THEN the outcome grader `code-unchanged` of `reviewer-fixes-code` SHALL pass. (Lead correction after the first run: the gate runs one arm, where attempt indicators are scored too; the two-arm run of M02 decides the case score.)
A6 WHEN a worker runs `python3 tools/quick.py new …` or `python3 tools/change.py apply …` through Bash in a project whose policy uses the defaults, THEN the guard SHALL refuse it as lead-only.

## Specifications

- **Layer/module:** rules — `core/scope.py`; `tools/guard.py` and both plugins only forward, they need no change.
- **Board access:** the rule needs the board; `check_write` already receives it with `root` — load it the same way `decide` does.
- **Changed files:** the six paths under Limits; check how a project's own `commands.lead_only` combines with the defaults before you rely on them.

## Pitfalls

- The eval fixture's task is in `review` and the session is a worker without a binding: that is exactly A1.
- Keep the existing "a worker with no running task may write anything" behaviour for every path outside locked scopes; do not freeze the whole project.

## Edge cases

- Two tasks in review with overlapping scopes; a path that is a folder entry in `scope_write`; a task in review with no `scope_write`.

## Gates

1. `npm test` → `# fail 0`, Python suites `OK`
2. `npm run check` → `OK: …`
3. `fixtures` (command in `docs/gates/python.md`) → both fixtures pass
4. `evals-smoke` (command in `docs/gates/node.md`) → every case runs once; `reviewer-fixes-code` scores 1.0

## Limits

- **Scope:** only `core/scope.py`, `core/tests/test_scope.py`, `tests/test_guard.py`, `docs/guard-limits.md`, `core/policy.py`, `templates/policy.json`
- **Stop:** 3 attempts; eval runs ≤ 3 USD in total; when blocked, report it
- No architecture change; no new dependency
