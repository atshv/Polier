# M11 — Owner decisions when no dialog appears

> Role: `backend-builder` — the same as `role` on the board.

## Goal

When the owner cannot see Polier's dialog (the Claude mobile app, a client without elicitation, a headless run), every owner decision still has a way that only a person can take, and no tool call blocks for an hour.

**Why:** in this line the lead dialog timed out twice after 3600 s in the Claude app; the owner had to switch the guard off to get anything done. Per the Claude Code docs, cloud-session dialogs appear as cards only at claude.ai/code and in the Desktop app's Code tab.

**Satisfies:** D1

**Operating the task:** claim → the lead sets `in_progress` → run the gates → `verifying` → `review` → `done` or `rework`. Approvals and escalation: `docs/orchestration.md`.

## Scope

- **Short dialog:** the Claude Code server gives an elicitation at most `POLIER_DIALOG_TIMEOUT` seconds (default 300); on timeout the outcome is `unanswered`, not a blocked call.
- **Pending record instead of a lost question:** `pl_mode lead/off`, `pl_factory init/advance` and `pl_approval` write a pending approval (`tools/approve.py request`; a new action `lead_mode` for the mode switch) when the dialog is unavailable or unanswered, and return its ID with the owner's way to answer.
- **A person-only answer:** plugin commands `commands/approve.md` and `commands/deny.md` (`/polier:approve AP-NNN`, `/polier:deny AP-NNN`) with `disable-model-invocation: true`, which run `tools/approve.py grant|deny` as the owner. Calling the same `pl_*` tool again then finds the granted record and proceeds.
- **Research first:** verify in the Claude Code docs, and with a real `claude -p --plugin-dir .` run, that a command with `disable-model-invocation: true` cannot be invoked by the model and that its `!` lines run when a person types it; record the result in `docs/research/human-only-commands.md`. If either fails, stop and report: the design changes.
- Tests in `plugin/test/`, `claude/test/` and `tests/test_approve_cli.py`; `docs/guard-limits.md` and `prompt/claude-code.md` describe the way.

## Out of scope

- DSH beyond keeping its approval prompt as it is; changing who may grant.

## Acceptance

A1 WHEN the dialog gets no answer within the timeout, THEN the tool SHALL return within it, with a pending approval ID and the command the owner types.
A2 WHEN the owner runs `/polier:approve AP-NNN` and the agent calls the same tool again, THEN the decision SHALL take effect and the record SHALL name the owner and "answered by command".
A3 WHEN the model tries to invoke the command (Skill or SlashCommand tool), THEN Claude Code SHALL refuse it (verified in the research note).
A4 WHEN a granted `lead_mode` record exists, THEN only the session that requested it SHALL switch (the record names the session key), once.
A5 WHEN a client offers elicitation and the owner answers in time, THEN the behaviour SHALL be unchanged.

## Pitfalls

- `.claude-plugin/plugin.json` is a protected path; the default `commands/` folder is scanned without a manifest key, so leave the manifest alone.
- A `!` line runs with the user's permissions: build the command from fixed arguments plus a validated `AP-\d{3,}` ID, nothing else.

## Edge cases

- Approve an ID that does not exist or is already decided; two pending `lead_mode` records; the server restarted between request and answer.
