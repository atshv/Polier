# Tool reference

> Generated by `node scripts/tools-doc.mjs` from `plugin/lib/tools.mjs`. Do not edit by hand.

The DeepSeek Harness plugin registers these tools for the model. The human never calls them: the agent maps plain language to them, and the ones that need a human decision open a DSH approval prompt.

## `pl_status`

The full Polier state as JSON: the factory line, the running task with scope and brief, ready tasks with handoffs, live claims, policy limits, pending approvals and open questions. The <polier> context already shows the summary; call this only when you need the details.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_gate`

Run one quality gate of a task through tools/gate.py. The full output goes to reviews/evidence/; the result shows pass/fail, the failing lines and the record path. The record path is the only accepted proof that a gate passed.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `task` | string | yes | Task ID, e.g. M03. |
| `gate` | string | yes | Gate name exactly as in the task's gates list, e.g. tests. |
| `command` | string | yes | Shell command of the gate, from AGENTS.md or the brief. |
| `timeout_s` | integer |  | Seconds before the gate is stopped. Default 600. |
| `lock_wait_s` | integer |  | Seconds to wait for an exclusive resource; default 0 (report busy at once). |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_scope_check`

Compare every changed file (git status) with the write scope of a task. Run it before you report a task as finished.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `task` | string |  | Task ID. Default: the bound or running task. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_check`

Run tools/check.py on the project: mandatory files, word budgets, board consistency, traceability, gate evidence and the factory line. ok: true means no errors.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_next`

The dispatch plan: running tasks with attempts, the next wave that can run in parallel, blocked tasks with what unblocks them, scope conflicts and pending approvals. Read it before starting a task.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `limit` | integer |  | Maximum tasks per wave. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_state`

Read the execution state of the board or of one task, or (lead session) move a task through one checkpoint: pending, in_progress, verifying, review, done, rework, blocked, failed. A refusal names what is missing. STATUS.md is regenerated after every change.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `task` | string |  | Task ID, e.g. M03. Without it and without status: the whole board. |
| `status` | string |  | New status. Omit to read. |
| `note` | string |  | Reason; required for rework, blocked and failed. |
| `force` | boolean |  | Override a checkpoint; needs a granted state_override approval. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_factory`

The factory line (factory.json). init shows the owner the planned line (platforms, traits, items per station) in an approval prompt and writes it only on yes. Read: status, next (open items of the current station with the evidence they need). Write (lead, or any session while no task runs): done (with evidence paths, optionally #heading), na or defer (with a reason), reopen, link (board tasks that deliver an item). advance asks the owner and closes the current station. Every write returns what is left and the next step; docs/factory.md is regenerated.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `action` | `init` · `status` · `next` · `done` · `na` · `defer` · `reopen` · `link` · `advance` |  | Default: next. |
| `platforms` | list of string |  | For init: web, ios, android, desktop, cli, service. |
| `traits` | list of string |  | For init: accounts, payments, personal_data, uploads, realtime, notifications, offline, i18n, ai, analytics, location, public, eu_users, cross_platform, brownfield. |
| `item` | string |  | Checklist item ID, e.g. BLD-30. |
| `evidence` | list of string |  | Project paths for done, e.g. docs/concept.md#user-stories. |
| `reason` | string |  | Reason for na or defer; a note for advance. |
| `tasks` | list of string |  | Board task IDs for link. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_mode`

Switch the role of this session. worker (default: writes only inside the running task's scope) and reviewer (writes only under reviews/) switch at once. lead (plans, merges, records state) and off (no guard) open an approval prompt for the owner first.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `role` | `worker` · `reviewer` · `lead` · `off` | yes |  |
| `reason` | string |  | Why the session needs this role; shown to the owner. |

## `pl_role`

Take a specialist role for this session (analyst, designer, architect, frontend-builder, backend-builder, mobile-builder, reviewer, security-reviewer, release-manager, or one the project adds in docs/roles/). The role adds its instructions to the system prompt, sets the session to worker or reviewer mode and may narrow where it writes; it never widens anything. Without role: drop it.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `role` | string |  | Role id. Omit to drop the role. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_task`

Bind this session to one task and take its claim, so the guard uses that task's scope and no other session works on it. A task with a role gives the session that role. Without task: release the binding and the claims of this session.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `task` | string |  | Task ID, e.g. M03. Omit to release. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## `pl_approval`

Ask the owner for a Polier approval (new_dependency, scope_change, merge_to_base, release, reopen_done, protected_path, state_override). Writes the request to reviews/approvals/, opens an approval prompt and records the owner's answer as granted or denied. Never act before it is granted.

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `action` | `new_dependency` · `scope_change` · `merge_to_base` · `release` · `reopen_done` · `protected_path` · `state_override` | yes |  |
| `task` | string |  | Task the approval is for; omit for project-wide. |
| `note` | string | yes | What exactly and why; shown to the owner. |
| `project` | string |  | Project folder. Default: the session directory or the nearest parent with board.json or factory.json. |

## The guide in the system prompt

Sessions inside a Polier project get this section:

```markdown
# Polier

This session is inside a Polier project: an AI software factory with nine stations (idea, concept, design, architecture, plan, build, verify, release, operate). The <polier> block in your context is the live state; read it instead of calling a status tool.

- The human speaks plainly ("weiter", "what is missing?", "build M03", "close the station"). Turn that into the matching Polier tool yourself; never ask the human to type a command.
- Records change only through tools: pl_factory (the line), pl_state (task status), pl_gate (evidence), pl_approval (approvals), pl_task (claims). Never edit factory.json, board.json, runs/ or reviews/approvals/ by hand. STATUS.md and docs/factory.md regenerate on their own.
- Human decisions are approval prompts, not chat: pl_mode lead, pl_factory advance and pl_approval open a prompt the owner answers. A "yes" in the chat is not an approval; call the tool.
- Evidence, not ticks: an item is done with a project file (optionally #heading) or with linked tasks that are done; must items are never deferred. A task is done with recorded gates, a passing review and a handoff.
- A whole station is long work: when goal tools exist and the human asks for it, create a goal such as "Close Polier station design: resolve every open item with evidence"; the <polier> block shows what is left each round.
- Specialists: a task names its role (frontend-builder, backend-builder, reviewer …). Delegate it to a fresh subagent whose first steps are pl_role with that role and pl_task with the task; pick the model strength the role suggests when the subagent tool lets you. A role only narrows what a session may do.
- Independent review: a fresh subagent in the reviewer role that sees only the brief, the diff and the gate records and writes reviews/<ID>.md.
- A Ralph or subagent report is a claim, not evidence: gates go through pl_gate and status through pl_state.
```
