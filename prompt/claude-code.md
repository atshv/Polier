# Claude Code: How Polier Runs Inside It

Polier runs in Claude Code as a plugin. This file maps the stations of `prompt/generator.md` and the running project to the Claude Code tools that do them best. It is the Claude Code counterpart of `prompt/dsh.md`; the process, the rules and the Python tools are the same.

> **Verified (2026-11-12)** against Claude Code 2.1.323 (the hooks, plugins, MCP and subagent references on code.claude.com, `claude plugin validate`, and real `claude -p --plugin-dir` runs on a throwaway project) and this package. Details the documentation does not state are marked `[UNVERIFIED]`.

## 0. What the plugin gives every session

| Seam | What Polier does with it |
|---|---|
| MCP server `polier` (`claude/server.mjs`) | The `pl_*` tools, named `mcp__plugin_polier_polier__pl_*`. They are the DSH plugin's tools (`plugin/lib/tools.mjs`); every write goes through `tools/*.py`. |
| MCP elicitation | Every owner decision is a dialog the person at the terminal answers: `pl_mode lead`/`off`, `pl_factory init`/`advance`, `pl_approval`. Without an interactive terminal (`claude -p`, a client without elicitation) it fails closed. |
| `SessionStart`, `SubagentStart` hooks | The guide and the live `<polier>` block, inside a Polier project only. A `polier:<role>` subagent is told to bind its role and task first. |
| `UserPromptSubmit` hook | The live `<polier>` block with every prompt: project, mode, role, station with open items, running task with scope and gates, ready tasks, limits, pending approvals, next move. |
| `PreToolUse` hook | `Write`, `Edit`, `MultiEdit`, `NotebookEdit` and `Bash` are checked by `tools/guard.py` (scope, role, policy); a denial is a `deny` (or `ask` with `enforce: ask`). A command that stops processes gets the kill warning once per prompt. |
| `Stop`, `SubagentStop` hooks | The stop check: git diff against the worker's scope; the turn continues with the list until the changes are undone or reported. A finished subagent releases its claims. |
| Subagents (`claude/agents/`) | One subagent type per role in `roles/roles.json`: `polier:frontend-builder`, `polier:reviewer` …, generated by `scripts/claude-plugin.py`. |
| Skill | The `polier` skill (`SKILL.md`). |

Session state (mode, specialist role, bound task, claims) lives in the MCP server's memory, one entry per Claude Code session and per subagent. The hooks read it over a local socket; only the `pl_*` tools change it. A new session starts as a worker.

The owner talks plainly ("weiter", "what is missing?", "close the station", "take M03"); the agent calls the matching tool. Every tool and parameter is in [`docs/tools.md`](../docs/tools.md).

## 1. What a session can do

| Capability | Tools |
|---|---|
| Files, shell, search | `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep` |
| Background jobs | `Bash` with `run_in_background`, `Monitor` |
| Structured questions | `AskUserQuestion` (up to 4 questions per call) |
| Plan mode | `EnterPlanMode`, `ExitPlanMode` (the owner approves the plan) |
| Checklist | `TaskCreate`, `TaskUpdate` (older versions: `TodoWrite`) |
| Web research | `WebSearch`, `WebFetch` |
| Subagents | `Agent` with a `subagent_type` (`polier:<role>`, `Explore`, `Plan`, `general-purpose`); `SendMessage` continues one |
| Worktrees | `Agent` with `isolation: "worktree"`, `EnterWorktree` / `ExitWorktree` |
| Deferred tools | `ToolSearch` loads a tool whose schema is not yet in context, e.g. `select:mcp__plugin_polier_polier__pl_status` |

- **Claude Code reads `CLAUDE.md`, not `AGENTS.md`.** A Polier project keeps its rules in `AGENTS.md` (the budget counts there) and puts a `CLAUDE.md` with the single line `@AGENTS.md` next to it; at L also in every package with its own `AGENTS.md`. `pl_preflight` warns when it is missing.
- **Plan mode and permission modes are guidance and convenience, not enforcement.** The Polier guard, `policy.json` and the owner dialogs decide what the plan allows.

## 2. Station → tool

| Station / step | Use | Fallback |
|---|---|---|
| start, after a break | `pl_preflight` | `tools/preflight.py` |
| all | `TaskCreate`, one task per station | none needed |
| 1 interview | `AskUserQuestion`, options with the recommended one first | chat |
| 1 start the line | `pl_factory` init (dialog) | owner: `! python3 <polier>/tools/factory.py init …` |
| 1–5 facts | `WebSearch`, `WebFetch`; record with `tools/research.py` | `[UNVERIFIED]` + ask |
| 1 brownfield recon | `Explore` subagents in parallel, one per top-level area | main session reads |
| 4+5 approval | `EnterPlanMode` + `ExitPlanMode`: architecture, DAG table, Mermaid (L: package map, stages, contracts) | chat, wait for "yes" |
| 4, 5 critics (M/L) | parallel subagents (`polier:architect`, `polier:security-reviewer`, `Plan`) that return findings only | one after another |
| 5 cold start + rubric | a fresh `general-purpose` subagent, continued with `SendMessage` | a second fresh subagent |
| 5 lint | `pl_check`, `pl_next` | `Bash` |
| 5 scaffold | `AGENTS.md` and `CLAUDE.md` (`@AGENTS.md`) | — |
| every close | `pl_factory advance` (dialog) | owner: `! python3 <polier>/tools/factory.py advance --by <owner>` |

Subagents only read, research and criticise during planning.

## 3. Running the project

| Step | Lead session | Worker subagent |
|---|---|---|
| choose | `pl_next` (waves, blocked tasks, conflicts) | — |
| start | worktree when required, `pl_state` → `in_progress` | `Agent` with `subagent_type: "polier:<role>"` and the task ID; its first calls are `pl_role`, `pl_task` |
| build | — | code inside the scope, `pl_gate` per gate, `pl_scope_check` |
| check | `pl_state` → `verifying`, `review` | — |
| review | a fresh `polier:reviewer` subagent with the `pl_review` packet, which appends a round to `reviews/M03.md` | — |
| close | `pl_state` → `done` (with handoff lines) or `rework`; `pl_factory done` for linked items; commit | — |

- **Specialists:** each role has a subagent type with the role's instructions and a model from its hint (`fast` → haiku, `standard` → sonnet, `strong` → opus). A role the project adds in `docs/roles/` runs as a `general-purpose` subagent that calls `pl_role` first. A role only narrows: it never grants lead or widens a scope.
- **Each subagent is its own Polier session.** Its mode starts as worker even when the main session is lead; it binds its own task and claim. When it finishes, its claims are released.
- **Gates:** `pl_gate` runs `tools/gate.py` as a plain process, passes the slot and locks the task's `exclusive` resources. Claude Code's sandbox, when enabled, covers `Bash`, not these processes `[UNVERIFIED]`.
- **Runtime:** ports, database and bucket from `.polier-slot` (`tools/slot.py show`). Never stop a process you did not start; the plugin warns once per prompt.
- **Budget:** Claude Code does not hand token counts to plugins: with a budget the lead records them with `tools/usage.py record <ID> --tokens N`.

**M — lead + 2–3 workers.** Workers are `polier:<role>` subagents, each with `isolation: "worktree"` or a worktree from `tools/worktree.py start`; several run in parallel when their scopes do not overlap. At most 3 workers.

**L — team + integrator.** As M, plus an integration branch with its own merge task and CI. Review lenses (correctness, security/data/tests) run as parallel reviewer subagents and merge into one `reviews/Mxx.md`.

## 4. Worktrees and slots

`tools/worktree.py start M03 --base main` (lead) makes branch, slot and claim and sets the task's `worktree`; a subagent working there is bound by that path. With `isolation: "worktree"` Claude Code makes its own worktree: take slot and claim inside it (`tools/slot.py acquire`, then `pl_task`). Shared runtime files and rules are those of `prompt/dsh.md` §4.

## 5. Approvals and security

- Closing a station, lead mode, `off` mode and every high-risk action (`new_dependency`, `release`, …) open a dialog; the record lands in `factory.json` or `reviews/approvals/` with `approved in Claude Code`.
- A dialog needs a person. In `claude -p`, in a client without elicitation, or when the owner cancels, nothing is granted. The owner can still decide with `! python3 <polier>/tools/approve.py grant AP-001 --by <name>` typed in the prompt: `!` runs a command as the person, not as the model.
- An `Elicitation` hook in the owner's settings can answer dialogs automatically. Polier cannot tell; do not configure one for the `polier` server.
- Releases are a human or CI action: no tag, publish or deploy from an agent session.
- The guard's limits are in [`docs/guard-limits.md`](../docs/guard-limits.md).

## 6. Installing and configuring

```text
/plugin marketplace add atshv/polier
/plugin install polier@polier
```

or, in one step on Claude Code 2.1.275 or later, `/plugin install polier --marketplace atshv/Polier`. Restart the session. Node 20+ and Python 3.9+ must be on the PATH. For a local checkout: `claude --plugin-dir /path/to/polier`.

Options (`/config`, or the dialog when the plugin is enabled):

| Option | Default | Meaning |
|---|---|---|
| `enforce` | `deny` | `deny` blocks, `ask` turns a denial into a permission prompt, `off` disables the guard |
| `stop_check`, `max_stop_reminders` | `true`, `2` | compare the git diff with the scope before a worker's turn ends |
| `python` | `python3` (`python` on Windows) | interpreter for the package tools and the guard |
| `owner` | `owner` | name written into records the owner answers |
| `context` | `true` | the `<polier>` block and the guide |

Status line (optional), in `~/.claude/settings.json`: `"statusLine": { "type": "command", "command": "node <polier>/claude/statusline.mjs" }`. It shows station, open items, running and ready tasks and the mode inside a Polier project.
